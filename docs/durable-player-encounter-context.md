# Durable player encounter context

The authenticated player path has a durable, server-owned source for the selection inputs needed by a player-versus-wild reservation.

`CanonicalPlayerEncounterProfile` stores a canonical player ID, an ordered canonical Pokemon roster, requested consumable item-instance quantities, an immutable `BattleArenaSnapshot`, and a profile revision. `FileCanonicalPlayerEncounterProfileRepository` stores that profile under the same world-scoped `autoptu/canonical-state` root used by canonical player, Pokemon and item persistence. Records are schema-versioned, keyed by a SHA-256 derivative of the canonical player ID, written through a forced temporary file plus atomic replacement, and protected by in-process and OS file locks. Revision replacement is compare-and-set and advances exactly once.

The profile is selection state, not asset authority. It does not certify that a Pokemon belongs to the player, that an item exists, that an item quantity is sufficient, or that a held item is usable. `BattleAuthorityService` still re-resolves every selected Pokemon and item through the canonical asset repositories, checks ownership and quantities, freezes revisions into the battle snapshot, and rejects stale or invalid reservations. The arena supplies only a dimension, origin, elevation and cardinal grid transform. It does not decide terrain, collision, movement, targeting, hazards or forced movement.

`FabricCanonicalPlayerProvisioning` now registers on Fabric's authenticated `ServerPlayConnectionEvents.JOIN` boundary. The connected player's UUID is converted into the stable canonical ID `minecraft-player:<uuid>`. On first join, the world-scoped player repository creates a revision-0 aggregate with empty Trainer classes, skills, Pokemon capabilities, Trainer Features and team plus zero AP and initiative modifier. That empty aggregate is deliberate fail-closed state. Repeated joins return the existing aggregate and never overwrite progression.

Minecraft contributes only the authenticated UUID to this provisioning step. Display/profile name, health, attributes, inventory, permissions, game mode, position and all other mutable `ServerPlayerEntity` fields are ignored. The adapter does not assign PTU classes, Features, Pokemon, items, AP, initiative bonuses, team membership or encounter selections from Minecraft. Later character-creation and progression services must make those changes through server-authoritative canonical mutations.

`PersistentCanonicalPlayerEncounterContextSource.fromWorldRuntime` is the production composition point for durable context. It obtains the canonical player and encounter-profile repositories from `FabricCanonicalPlayerStoreRuntime` for the exact live `MinecraftServer`. `FabricAuthenticatedPlayerContextResolver.persistentWorld` then requires the external PLAYER UUID to resolve to a currently connected player through `MinecraftServer.getPlayerManager()` before that durable context can be read. `CobblemonPlayerVsWildClaimCoordinator.persistentWorld` composes the authenticated resolver with the existing player-versus-wild authority service.

The resulting path is: authenticated Minecraft join -> deterministic canonical player ID -> durable player aggregate -> later Cobblemon PLAYER actor UUID -> Minecraft online-player check -> canonical identity registry -> durable player aggregate -> durable encounter profile -> canonical roster/item/arena request -> `BattleAuthorityService` asset revalidation -> composed player-versus-wild reservation. No `ServerPlayerEntity` stat, inventory slot, permission, position, Cobblemon Pokemon value or client packet field becomes trusted PTU state.

The existing compatibility feature `AUTHENTICATED_PLAYER_CONTEXT_RESOLUTION` covers both login-time canonical provisioning and encounter-time authentication. `AuthenticatedPlayerProvisioningCompatibility` binds the new provisioning slice to that same permanent matrix entry. It consumes only `MINECRAFT_COBBLEMON_CRAFTICS_ADAPTER_PLAYBACK`, which remains PARTIAL, and introduces no dependency on forced movement or tactical AI.

The headless production authentication smoke constructs the same world-backed persistent resolver used by the production composition while verifying the fail-closed offline/malformed identity path. Unit coverage verifies stable UUID-to-canonical identity, fail-closed first-state creation and that reconnects cannot overwrite existing progression. The two-process restart smoke separately proves that Trainer, encounter profile, Pokemon, item quantity and an active item reservation survive reopening the same Minecraft world.

Still deferred: automatic encounter-profile/Pokemon identity provisioning, a logged-in graphical client fixture, successful live PLAYER-vs-WILD execution, cross-aggregate journaling/recovery, reservation reconciliation/expiry, and `RuntimeCombatantState` materialization. Move effects, abilities, item effects, Trainer Feature execution, terrain semantics, status lifecycle, forced movement, reactions and tactical AI remain owned by AutoPTU-Java and are not approximated here.
